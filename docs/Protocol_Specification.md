# UDP Protocol Specification

## 1. Назначение протокола

Протокол предназначен для обмена данными между клиентом и выделенным сервером в сетевой игре с видом сверху, посвящённой гонкам.

Для передачи игровых команд используется протокол UDP. UDP выбран из-за небольшой задержки и отсутствия необходимости устанавливать постоянное соединение. Для игровой логики важнее актуальность данных, чем гарантированная доставка каждого отдельного пакета.

Протокол поддерживает следующие типы сообщений:

* MOVEMENT — передача координат автомобиля;
* SHOOT — команда использования оружия;
* STATE — передача сервером актуального состояния игрока;
* ACK — подтверждение получения команды;
* PING — запрос для измерения сетевой задержки;
* PONG — ответ сервера на PING.

---

## 2. Общая структура пакета

Каждый пакет начинается с заголовка `PacketHeader`.

Размер заголовка — 7 байт.

| Поле          |  Размер | Описание                 |
| ------------- | ------: | ------------------------ |
| `type`        |  1 байт | Тип пакета               |
| `sequence`    | 2 байта | Порядковый номер пакета  |
| `payloadSize` | 2 байта | Размер полезной нагрузки |
| `version`     | 2 байта | Версия протокола         |

Обязательными полями заголовка являются `type`, `sequence` и `payloadSize`. Поле `version` используется текущей реализацией для контроля совместимости версий протокола.

Для целочисленных полей размером 2, 4 и 8 байт используется сетевой порядок байтов (Network Byte Order, Big Endian).

Для передачи координат типа `float` используется преобразование битового представления числа в `uint32_t`, после чего к полученному целому числу применяется `htonl()`/`ntohl()`.

Для 16- и 64-битных значений в пакетах телеметрии используются специальные функции сериализации `WriteU16`, `WriteU64`, `ReadU16` и `ReadU64`.

---

## 3. Типы пакетов

| Значение | Тип      | Назначение                         |
| -------: | -------- | ---------------------------------- |
|      `1` | MOVEMENT | Передача координат автомобиля      |
|      `2` | SHOOT    | Команда стрельбы                   |
|      `3` | STATE    | Передача состояния игрока          |
|      `4` | ACK      | Подтверждение получения команды    |
|      `5` | PING     | Запрос измерения сетевой задержки  |
|      `6` | PONG     | Ответ на PING с временными метками |

Версия текущего протокола:

`1`

---

## 4. Пакет MOVEMENT

Пакет используется клиентом для передачи серверу координат автомобиля.

### Заголовок

* `type = 1`
* `payloadSize = 12 байт`
* `sequence` — порядковый номер пакета
* `version = 1`

### Полезная нагрузка

| Поле |  Размер | Описание     |
| ---- | ------: | ------------ |
| `x`  | 4 байта | Координата X |
| `y`  | 4 байта | Координата Y |
| `z`  | 4 байта | Координата Z |

Размер полезной нагрузки:

`12 байт`

Общий размер пакета:

`7 + 12 = 19 байт`

После получения MOVEMENT сервер извлекает координаты, обрабатывает команду и отправляет клиенту пакет STATE.

---

## 5. Пакет SHOOT

Пакет используется клиентом для передачи команды стрельбы.

### Заголовок

* `type = 2`
* `payloadSize = 1 байт`
* `sequence` — порядковый номер пакета
* `version = 1`

### Полезная нагрузка

| Поле       | Размер | Описание             |
| ---------- | -----: | -------------------- |
| `weaponId` | 1 байт | Идентификатор оружия |

Размер полезной нагрузки:

`1 байт`

Общий размер пакета:

`7 + 1 = 8 байт`

После получения SHOOT сервер выводит команду в журнал и отправляет клиенту ACK.

---

## 6. Пакет STATE

Пакет отправляется сервером в ответ на MOVEMENT и содержит состояние игрока.

### Заголовок

* `type = 3`
* `payloadSize = 14 байт`
* `sequence` — соответствует последовательности исходного пакета
* `version = 1`

### Полезная нагрузка

| Поле       |  Размер | Описание             |
| ---------- | ------: | -------------------- |
| `playerId` | 2 байта | Идентификатор игрока |
| `x`        | 4 байта | Координата X         |
| `y`        | 4 байта | Координата Y         |
| `z`        | 4 байта | Координата Z         |

Размер полезной нагрузки:

`2 + 4 + 4 + 4 = 14 байт`

Общий размер пакета:

`7 + 14 = 21 байт`

---

## 7. Пакет ACK

Пакет используется сервером для подтверждения получения команды SHOOT.

### Заголовок

* `type = 4`
* `payloadSize = 0 байт`
* `sequence` — соответствует исходному пакету
* `version = 1`

Полезная нагрузка отсутствует.

Общий размер пакета:

`7 байт`

---

## 8. Пакет PING

Пакет PING используется клиентом для измерения времени прохождения данных до сервера и обратно.

### Заголовок

* `type = 5`
* `sequence` — уникальный порядковый номер измерения
* `payloadSize = 8 байт`
* `version = 1`

### Полезная нагрузка

| Поле               | Размер | Описание                                  |
| ------------------ | -----: | ----------------------------------------- |
| `clientSendTimeUs` | 8 байт | Время отправки PING по часам клиента, мкс |

Размер полезной нагрузки:

`8 байт`

Общий размер пакета:

`7 + 8 = 15 байт`

`clientSendTimeUs` записывается непосредственно перед отправкой PING.

---

## 9. Пакет PONG

Пакет PONG отправляется сервером в ответ на корректно полученный PING.

### Заголовок

* `type = 6`
* `sequence` — соответствует исходному PING
* `payloadSize = 24 байта`
* `version = 1`

### Полезная нагрузка

| Поле                  | Размер | Описание                      |
| --------------------- | -----: | ----------------------------- |
| `clientSendTimeUs`    | 8 байт | Исходное время отправки PING  |
| `serverReceiveTimeUs` | 8 байт | Время получения PING сервером |
| `serverSendTimeUs`    | 8 байт | Время отправки PONG сервером  |

Размер полезной нагрузки:

`8 + 8 + 8 = 24 байта`

Общий размер пакета:

`7 + 24 = 31 байт`

Сервер возвращает исходный `clientSendTimeUs`, чтобы клиент мог проверить соответствие ответа отправленному PING.

---

## 10. Измерение RTT

RTT измеряется на стороне клиента.

При отправке PING клиент фиксирует:

`clientSendTimeUs`

После получения PONG клиент фиксирует текущее время:

`clientReceiveTimeUs`

RTT рассчитывается по формуле:

`RTT = clientReceiveTimeUs - clientSendTimeUs`

Время сервера не используется непосредственно для расчёта RTT.

Это позволяет не требовать синхронизации часов клиента и сервера.

Для измерений используется `std::chrono::steady_clock`, который предназначен для измерения интервалов времени и не зависит от изменения системных часов.

---

## 11. Сглаженное RTT

Для получения более стабильной оценки задержки используется SRTT (Smoothed Round-Trip Time).

Первое полученное значение RTT используется для инициализации SRTT.

Для последующих измерений применяется формула:

`SRTT = 0.875 × SRTT_previous + 0.125 × RTT`

Таким образом, последнее измерение влияет на значение SRTT, но не заменяет полностью предыдущую оценку.

---

## 12. Контроль тайм-аута

Для каждого отправленного PING клиент сохраняет информацию о запросе:

* `sequence`;
* время отправки;
* идентификатор экспериментальной серии;
* статус;
* количество попыток.

Тайм-аут ожидания PONG составляет:

`1000 мс`

Если ответ не получен в течение этого времени, запрос получает статус `timeout`.

Повторная отправка PING после тайм-аута в рамках практической работы №2 не выполняется.

---

## 13. Статусы ответа

Для анализа результатов используются следующие статусы:

| Статус      | Описание                                      |
| ----------- | --------------------------------------------- |
| `received`  | PONG получен вовремя                          |
| `timeout`   | PONG не получен в течение тайм-аута           |
| `late`      | PONG получен после истечения тайм-аута        |
| `duplicate` | Повторный PONG для уже обработанного запроса  |
| `unknown`   | PONG относится к неизвестному sequence number |

---

## 14. Сериализация PING/PONG

Для телеметрических пакетов не используется прямая передача C++-структуры в UDP-буфер.

Вместо этого каждое поле сериализуется явно.

Используются функции:

```text
WriteU16
WriteU64
ReadU16
ReadU64
```

16-битные и 64-битные целые значения записываются в сетевом порядке байтов.

При чтении выполняется обратное преобразование.

Такой подход позволяет явно контролировать размер пакета, порядок байтов и границы буфера.

---

## 15. Проверка пакетов PING/PONG

При обработке PING и PONG выполняется проверка:

* минимального размера заголовка;
* типа пакета;
* версии протокола;
* размера полезной нагрузки;
* фактического размера UDP-датаграммы;
* выхода полей за границы полученного буфера.

Для PING ожидается:

`payloadSize = 8`

Для PONG ожидается:

`payloadSize = 24`

Если проверка не пройдена, пакет считается некорректным и отбрасывается.

---

## 16. Последовательность обмена PING/PONG

```text
Client                              Server

  |                                   |
  |------------ PING ---------------->|
  |                                   |
  |                         получение PING
  |                         фиксация времени
  |                         применение задержки
  |                                   |
  |<----------- PONG -----------------|
  |                                   |
  |             фиксация времени      |
  |             расчёт RTT            |
  |                                   |
```

При каждом новом измерении клиент использует новый `sequence`.

---

## 17. Последовательный номер

Каждый отправляемый клиентом пакет получает порядковый номер `sequence`.

Для PING каждый новый запрос получает новое значение `sequence`.

Сервер сохраняет этот номер в ответном PONG.

Это позволяет клиенту сопоставить полученный PONG с исходным PING.

Для отслеживания одновременно отправленных запросов используется таблица `inFlight`.

Максимальное количество одновременно отслеживаемых запросов:

`256`

---

## 18. Проверка версии протокола

Каждый пакет содержит поле `version`.

Сервер сравнивает полученную версию с поддерживаемой версией протокола.

В текущей реализации поддерживается:

`version = 1`

Если версия не поддерживается, пакет отклоняется.

---

## 19. Обработка некорректных пакетов

Сервер и клиент выполняют проверку входящих пакетов перед обработкой.

Проверяются:

* минимальный размер заголовка;
* тип команды;
* версия протокола;
* размер полезной нагрузки;
* соответствие фактического размера пакета размеру заголовка и указанной полезной нагрузки;
* корректность границ буфера.

При обнаружении некорректного пакета соответствующая команда не выполняется, а пакет отбрасывается.

---

## 20. Журналирование

Сервер выводит в консоль информацию о полученных пакетах.

Для игровых пакетов может отображаться:

* тип пакета;
* порядковый номер;
* размер полезной нагрузки;
* версия протокола;
* координаты для MOVEMENT;
* идентификатор оружия для SHOOT;
* результат отправки ответа.

Для PING/PONG дополнительно могут использоваться временные метки, необходимые для диагностики измерений.

## 22. Ограничения текущей версии

Текущая версия протокола является учебной реализацией.

В ней не реализованы:

* авторизация клиента;
* шифрование;
* CRC32 или другая контрольная сумма;
* повторная передача потерянных игровых пакетов;
* защита от повторной отправки игровых пакетов;
* интерполяция состояния автомобиля;
* управление несколькими игровыми сессиями;
* синхронизация часов клиента и сервера.

Для практической работы №2 повторная передача PING после тайм-аута также не используется, поскольку задача эксперимента заключается в измерении задержки и качества UDP-соединения, а не в обеспечении гарантированной доставки.

Эти возможности могут быть добавлены в последующих версиях протокола.
