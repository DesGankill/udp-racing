# Latency Report

## 1. Общая информация

**Практическая работа:** №2
**Тема:** Инженерное измерение RTT и анализ качества UDP-соединения
**Язык:** C++17
**Транспортный протокол:** UDP
**Количество серий:** 6
**Количество PING в каждой серии:** 50
**Интервал между PING:** 500 мс
**Тайм-аут ожидания PONG:** 1000 мс

Для измерения времени использовались часы клиента на основе `std::chrono::steady_clock`.

---

## 2. Методика измерения

Измерение выполняется посредством обмена двумя типами пакетов:

* `PING` — отправляется клиентом серверу;
* `PONG` — формируется сервером и отправляется обратно клиенту.

При отправке PING клиент записывает время отправки `clientSendTimeUs`.

Сервер при получении PING фиксирует `serverReceiveTimeUs`, после чего при необходимости применяет искусственную сетевую задержку. Непосредственно перед отправкой PONG сервер фиксирует `serverSendTimeUs`.

После получения PONG клиент фиксирует время получения и рассчитывает RTT:

`RTT = clientReceiveTimeUs - clientSendTimeUs`

Таким образом, для расчёта RTT не требуется синхронизация часов клиента и сервера.

Для последовательных измерений рассчитывается сглаженное значение RTT:

`SRTT = 0.875 × SRTT_previous + 0.125 × RTT`

Для первого полученного ответа значение SRTT устанавливается равным первому измеренному RTT.

Джиттер рассчитывается как средняя абсолютная разница между соседними значениями RTT:

`Jitter = 1/(n-1) × Σ|RTT_i - RTT_(i-1)|`

Потери определяются по количеству PING, для которых не был получен PONG в течение 1000 мс:

`Loss = N_timeout / N_sent × 100%`

## 3. Экспериментальные серии

Были выполнены следующие серии измерений:

| Серия       | Условия                                   |
| ----------- | ----------------------------------------- |
| `baseline`  | Без искусственного воздействия на сеть    |
| `delay_50`  | Дополнительная задержка 50 мс             |
| `delay_100` | Дополнительная задержка 100 мс            |
| `jitter`    | Задержка 50 мс с изменением ±20 мс        |
| `loss_5`    | Вероятность потери пакета 5%              |
| `combined`  | Задержка 50 мс, jitter ±20 мс и потери 5% |

Для каждой серии было отправлено 50 PING.

## 5. Анализ результатов

### 5.1. Baseline

В базовом эксперименте без искусственной задержки все 50 PING получили соответствующий PONG.

Средний RTT составил 5.411 мс, медианный RTT — 4.494 мс.

Максимальное значение RTT составило 40.800 мс. Оно значительно выше основной части измерений и показывает наличие кратковременного системного скачка задержки.

Потерь пакетов в базовой серии не обнаружено.

### 5.2. Delay 50 ms

При добавлении искусственной задержки 50 мс средний RTT составил 73.861 мс, а медиана — 78.261 мс.

По сравнению с baseline наблюдается существенное увеличение задержки, что соответствует ожидаемому эффекту применения искусственной задержки на сервере.

Все 50 запросов получили ответы, поэтому потери в данной серии отсутствовали.

### 5.3. Delay 100 ms

При искусственной задержке 100 мс медианный RTT составил 110.177 мс.

Среднее значение оказалось выше и составило 125.241 мс. Максимальное значение — 779.311 мс — является выраженным выбросом.

Данный выброс существенно увеличивает среднее значение, поэтому медиана лучше характеризует типичную задержку в данной серии.

Также в серии было зарегистрировано 3 тайм-аута из 50 запросов. Это соответствует фактическому уровню потерь 6%.

### 5.4. Jitter

В серии `jitter` использовалась базовая искусственная задержка 50 мс с дополнительным изменением задержки в диапазоне ±20 мс.

Полученный RTT находился в диапазоне от 46.842 до 96.245 мс.

Средний RTT составил 74.600 мс, медианный — 78.757 мс.

Изменение задержки между последовательными пакетами привело к увеличению джиттера по сравнению со стабильной серией `delay_50`.

### 5.5. Loss 5%

В эксперименте `loss_5` применялась вероятность потери пакета 5%.

Из 50 отправленных PING было получено 47 PONG, а 3 запроса завершились тайм-аутом.

Фактическая доля потерь составила:

`3 / 50 × 100% = 6%`

Полученное значение отличается от заданных 5%, поскольку при количестве всего 50 испытаний число потерянных пакетов является дискретным. Три потерянных пакета соответствуют 6% от общего количества.

### 5.6. Combined

В комбинированной серии одновременно применялись:

* задержка 50 мс;
* jitter ±20 мс;
* вероятность потери 5%.

Из 50 PING было получено 47 PONG, 3 запроса завершились тайм-аутом.

Средний RTT составил 73.481 мс, медианный RTT — 78.964 мс.

Диапазон полученных RTT составил от 47.818 до 95.990 мс, что соответствует наличию переменной задержки.

---

## 6. Анализ SRTT и jitter

Сглаженное значение RTT позволяет уменьшить влияние отдельных скачков задержки.

Наиболее выраженные изменения RTT наблюдались в сериях с искусственным jitter и в комбинированном сценарии.

В серии `delay_100` наличие значения 779.311 мс показывает, что единичный сетевой или системный выброс может существенно влиять на среднее значение RTT. При этом медиана 110.177 мс остаётся близкой к ожидаемой задержке.

Поэтому при анализе сетевых измерений целесообразно рассматривать одновременно среднее значение, медиану и диапазон значений.

В серии `delay_100` также были зарегистрированы три тайм-аута. Это показывает, что в реальной среде на результаты эксперимента могут влиять не только искусственные сетевые условия, но и временные задержки обработки или планирования процессов операционной системой.

## 8. Вывод

В ходе практической работы был реализован механизм измерения задержки UDP-соединения с использованием обмена PING/PONG.

Были реализованы:

* измерение RTT по часам клиента;
* расчёт SRTT;
* расчёт jitter;
* контроль тайм-аутов;
* фиксация потерянных ответов;
* обработка поздних и дублирующихся ответов;
* моделирование задержки, jitter и потерь;
* запись результатов измерений в CSV;
* построение графиков для анализа результатов.

Проведённые эксперименты показали ожидаемое влияние искусственной задержки и потерь на характеристики UDP-соединения.

При увеличении искусственной задержки увеличивался RTT. Добавление jitter приводило к увеличению разброса RTT. При включении потерь часть запросов завершалась тайм-аутом.

Также эксперимент показал влияние единичных выбросов на среднее значение RTT. Поэтому для анализа сетевых измерений полезно использовать не только среднее, но и медианное значение, а также рассматривать диапазон распределения измерений.

Полученные результаты подтверждают работоспособность реализованного механизма измерения и позволяют использовать его для количественного анализа качества UDP-соединения.
