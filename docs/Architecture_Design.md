# Architecture Design

## 1. Назначение системы

Разрабатываемая система является сетевой основой для 2D игры-гонки с видом сверху.

Игрок управляет автомобилем, а обмен игровыми данными между клиентом и сервером выполняется по протоколу UDP.

Основная задача текущей реализации — продемонстрировать двусторонний обмен командами между клиентом и сервером, обработку игровых сообщений и передачу состояния игрока.

В дальнейшем данная сетевой основа может быть расширена до полноценной многопользовательской игры.

---

## 2. Выбранная топология

Для проекта используется топология **Dedicated Server**.

В данной архитектуре сервер является отдельным процессом и отвечает за обработку игровых команд и состояние игрового мира.

Клиенты не взаимодействуют друг с другом напрямую.

Схема взаимодействия:

```text
                 ┌──────────────────┐
                 │ Dedicated Server │
                 │                  │
                 │ UDP : 54000      │
                 └────────┬─────────┘
                          │
                ┌─────────┴─────────┐
                │                   │
         ┌──────▼──────┐     ┌──────▼──────┐
         │   Client 1  │     │   Client 2  │
         │              │     │              │
         │ UDP          │     │ UDP          │
         └──────────────┘     └──────────────┘
```

Текущая демонстрационная версия использует одного клиента, но архитектура допускает подключение нескольких клиентов.

---

## 3. Причины выбора Dedicated Server

Выделенный сервер позволяет централизовать обработку игрового состояния.

Основные функции сервера:

* получение команд клиентов;
* проверка корректности пакетов;
* обработка игровых команд;
* формирование ответов;
* хранение актуального состояния игроков;
* журналирование полученных команд.

Сервер является **авторитетным источником состояния игрового мира**. Клиент передаёт серверу команды управления, но окончательное состояние автомобиля и игрового мира определяется сервером.

Клиент отвечает преимущественно за обработку пользовательского ввода, отправку команд, получение состояния и его отображение.

Такой подход уменьшает зависимость игрового состояния от конкретного клиента и позволяет централизованно синхронизировать игроков.

---

## 4. Выбор UDP

Для сетевого обмена используется UDP.

UDP подходит для игровой системы, поскольку игровые данные должны передаваться с минимальной задержкой.

В случае потери отдельного пакета более актуальным является получение следующего состояния автомобиля, чем повторная доставка устаревшей информации.

В текущем протоколе используется поле `SequenceNumber`, которое позволяет сопоставлять ответы сервера с отправленными командами.

---

## 5. Основные компоненты

Система разделена на несколько компонентов.

### 5.1. Client

Файл:

```text
src/client.cpp
```

Отвечает за:

* создание UDP-сокета;
* формирование игровых команд;
* сериализацию пакетов;
* отправку пакетов серверу;
* получение ответов;
* десериализацию состояния;
* вывод результатов обмена.

В демонстрационной версии клиент автоматически отправляет команды с интервалом в одну секунду.

В целевой версии клиент также будет отвечать за получение пользовательского ввода и передачу команд управления автомобилем.

---

### 5.2. Server

Файл:

```text
src/server.cpp
```

Отвечает за:

* инициализацию Winsock;
* создание UDP-сокета;
* привязку к порту `54000`;
* получение UDP-пакетов;
* передачу пакетов обработчику;
* завершение работы сокета.

Основная задача `server.cpp` — организация сетевого цикла.

В целевой версии сервер также будет управлять игровым миром и состояниями подключённых игроков.

---

### 5.3. Packet Handler

Файл:

```text
src/packet_handler.h
```

Отвечает за обработку уже полученного пакета.

Основные задачи:

* проверка размера пакета;
* чтение заголовка;
* проверка версии протокола;
* определение типа команды;
* обработка `MOVEMENT`;
* обработка `SHOOT`;
* формирование `STATE`;
* формирование `ACK`;
* отправка ответа клиенту;
* журналирование команд.

Выделение обработчика отдельно позволяет не помещать всю логику обработки пакетов непосредственно в `main()` сервера.

---

### 5.4. Protocol

Файл:

```text
src/protocol.h
```

Содержит общие определения протокола:

* типы пакетов;
* структуру заголовка;
* структуры полезной нагрузки;
* версию протокола;
* функции преобразования числовых данных в сетевой формат.

Таким образом, описание формата пакетов находится в одном месте и используется как клиентом, так и сервером.

---

## 6. Основные игровые сущности

В целевой версии игры предполагается разделение сетевой и игровой логики на несколько основных сущностей.

### 6.1. Player

Представляет игрока в игровой сессии.

Основные обязанности:

* хранение идентификатора игрока;
* связь игрока с управляемым автомобилем;
* хранение состояния игрока;
* обработка входящих команд управления.

---

### 6.2. Vehicle

Представляет автомобиль игрока.

Основные обязанности:

* хранение позиции и ориентации;
* хранение скорости;
* обработка команд управления;
* обновление состояния автомобиля;
* предоставление текущего состояния для синхронизации.

---

### 6.3. World

Представляет игровое пространство.

Основные обязанности:

* хранение объектов игрового мира;
* хранение автомобилей игроков;
* обновление состояния объектов;
* обработка столкновений и других игровых взаимодействий;
* предоставление актуального состояния игрового мира серверу.

---

### 6.4. GameServer

Представляет основной серверный компонент игры.

Основные обязанности:

* управление игровой сессией;
* хранение списка подключённых игроков;
* получение сетевых команд;
* передача команд игровым объектам;
* обновление игрового мира;
* формирование состояния для клиентов.

`GameServer` является частью серверной логики будущей игры и не реализуется полностью в текущем демонстрационном прототипе.

---

### 6.5. NetworkClient

Отвечает за сетевое взаимодействие клиента с сервером.

Основные обязанности:

* формирование сетевых пакетов;
* сериализация команд;
* отправка UDP-пакетов;
* получение ответов сервера;
* десериализация состояния;
* передача полученного состояния игровым системам клиента.

В текущей демонстрационной версии соответствующая логика находится в `client.cpp`.

---

### 6.6. InputController

Отвечает за получение пользовательского ввода.

Основные обязанности:

* обработка нажатий клавиш;
* формирование команд управления автомобилем;
* передача команд в сетевой слой клиента.

В текущей демонстрационной версии пользовательский ввод не реализован, а команды формируются автоматически.

---

### 6.7. ClientRenderer

Отвечает за визуальное отображение состояния игры на стороне клиента.

Основные обязанности:

* отображение игрового мира;
* отображение автомобилей;
* обновление положения объектов на основе состояния сервера;
* отображение результатов игровых действий.

`ClientRenderer` не изменяет авторитетное состояние игрового мира.

---

## 7. Распределение обязанностей

Основное распределение ответственности между клиентом и сервером:

```text
                    GAME SERVER
                         │
              ┌──────────┴──────────┐
              │                     │
            World               GameServer
              │                     │
              │             обработка команд
              │             управление игроками
              │
          ┌───┴───┐
          │       │
       Player   Vehicle
          │       │
          └───┬───┘
              │
        авторитетное
           состояние
              │
             UDP
              │
              ▼
            CLIENT
              │
      ┌───────┼────────┐
      │       │        │
 InputController NetworkClient ClientRenderer
      │       │        │
      │       │        └── отображение
      │       │
      │       └── получение состояния
      │
      └── формирование команд
```

Клиент отвечает за ввод, сетевой обмен и отображение.

Сервер отвечает за игровую логику, обработку команд и авторитетное состояние мира.

---

## 8. Принцип разделения ответственности

В проекте применяется принцип разделения ответственности.

Условно текущая система разделена следующим образом:

```text
Client
  │
  ├── формирование команды
  ├── сериализация
  ├── отправка
  │
  ▼
UDP
  │
  ▼
Server
  │
  ├── получение
  └── передача обработчику
           │
           ▼
     Packet Handler
           │
           ├── проверка
           ├── обработка
           └── формирование ответа
                    │
                    ▼
                   UDP
                    │
                    ▼
                  Client
```

Такое разделение позволяет отделить сетевой цикл от обработки протокола.

В целевой архитектуре аналогичный принцип применяется к игровым компонентам: ввод, сетевое взаимодействие, игровая логика и отображение имеют отдельные обязанности.

---

## 9. Жизненный цикл пакета

### 9.1. Отправка MOVEMENT

1. Клиент формирует координаты автомобиля.
2. Создаётся заголовок пакета.
3. Координаты преобразуются в сетевой формат.
4. Заголовок и полезная нагрузка объединяются в UDP-пакет.
5. Пакет отправляется серверу.
6. Сервер получает пакет.
7. `Packet Handler` проверяет его корректность.
8. Сервер извлекает координаты.
9. Формируется пакет `STATE`.
10. `STATE` отправляется клиенту.
11. Клиент получает пакет и восстанавливает координаты.

---

### 9.2. Отправка SHOOT

1. Клиент формирует команду `SHOOT`.
2. В пакет помещается идентификатор оружия.
3. Пакет отправляется серверу.
4. Сервер определяет тип команды.
5. Сервер извлекает `weaponId`.
6. Команда записывается в журнал.
7. Сервер формирует `ACK`.
8. `ACK` отправляется клиенту.
9. Клиент выводит подтверждение.

---

## 10. Сериализация

Для обеспечения одинакового представления данных между сторонами используется сетевой порядок байтов.

Для полей размером 16 бит используются:

```cpp
htons()
ntohs()
```

Для 32-битных значений используются:

```cpp
htonl()
ntohl()
```

Координаты `float` преобразуются следующим образом:

```text
float
  ↓
битовое представление uint32_t
  ↓
htonl()
  ↓
UDP
  ↓
ntohl()
  ↓
uint32_t
  ↓
float
```

Это позволяет явно контролировать порядок байтов при передаче координат.

Для определения размеров и выравнивания структур протокола используется упаковка `#pragma pack(push, 1)`.

## 11. Производительность и частота обмена

В демонстрационной версии клиент отправляет команды один раз в секунду.

Для целевой игровой системы предполагается следующая модель:

| Компонент               |                   Частота |
| ----------------------- | ------------------------: |
| Клиентский игровой цикл |                    60 FPS |
| Серверная обработка     |                     30 Hz |
| Сетевая отправка команд | зависит от состояния игры |

При дальнейшем развитии проекта сетевой обмен может быть отделён от визуального игрового цикла.

---

## 12. Масштабирование

Архитектура рассчитана на небольшие игровые сессии.

Предполагаемое количество игроков:

**2–8 игроков на сессию.**

В целевой версии сервер хранит состояние каждого подключённого игрока и отправляет актуальные данные клиентам.

При увеличении количества игроков могут потребоваться:

* идентификация клиентов;
* управление игровыми сессиями;
* отдельные состояния игроков;
* частичная синхронизация состояния;
* ограничение частоты отправки;
* обработка потери и задержки пакетов.

---

## 13. Безопасность и надёжность

Текущая версия предназначена для демонстрации сетевого протокола и не является полноценной защищённой системой.

В будущем могут быть добавлены:

* авторизация клиента;
* идентификатор игровой сессии;
* CRC32;
* защита от повторных пакетов;
* проверка допустимости координат;
* ограничение частоты команд;
* шифрование сетевого трафика.

## 15. Итог

Выбранная архитектура использует выделенный сервер и UDP для обмена игровыми командами.

Клиент отправляет команды `MOVEMENT` и `SHOOT`.

Сервер принимает и обрабатывает команды, после чего возвращает `STATE` или `ACK`.

Сервер является авторитетным источником состояния игрового мира, а клиент отвечает за ввод, сетевое взаимодействие и отображение полученного состояния.

Разделение сетевого цикла, обработки пакетов, определения протокола и будущих игровых компонентов позволяет сохранить код достаточно простым и одновременно обеспечить разделение ответственности между основными компонентами системы.
